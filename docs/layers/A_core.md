# Слой A. Foundation (`td::core`): разбор кода

Самый нижний слой. Он ничего не знает про башни, врагов, карты, Godot и файлы,
зависит только от стандартной библиотеки. Из него строятся все остальные слои.
Описание блока: `docs/design/A_foundation_detailed.md`.

В описании 26 классов. Написаны 13: те, которые используют слои B (определения)
и C (валидация). Остальные 13 добавляются в слоях, где они впервые нужны
(таблица в `docs/ARCHITECTURE.md`).

## Структура

```
modules/core/
  include/td/core/   публичные заголовки (подключаются как "td/core/Tick.h")
  src/               реализации (.cpp), где логика длиннее пары строк
  tests/             Catch2, 7 файлов, 50 тест-кейсов
```

`.cpp` есть у `Numeric`, `FixedTimeStep`, `Version`, `Diagnostic` (вместе с `DiagnosticList`).
Остальные классы короткие и целиком лежат в заголовке.

## Три сквозные идеи слоя

1. **Невалидное значение нельзя создать.** Конструктор закрыт, значение создаётся
   через фабрику, которая возвращает `Result` (`ConfigId::tryParse`,
   `FixedTimeStep::create`, `Version::parse`). Проверка записана один раз, а не в
   десяти валидаторах.
2. **Ожидаемые ошибки возвращаются, нарушения контракта бросаются.** Плохой ввод
   это `Result` с `Diagnostic`. Программная ошибка (`Tick(-1)`, `value()` у
   неуспешного `Result`, круг с нулевым радиусом) бросает исключение.
3. **Детерминизм.** Одинаковые входные данные дают одинаковый результат на любой
   машине: упорядоченный `std::map`, фиксированный порядок соседей, округление с
   допуском, числа спрятаны за `Scalar`.

## Классы по группам

### Идентификаторы

- `ConfigId<Tag>` (`ConfigId.h`): строковый id по шаблону `[a-z0-9_]+`. `Tag` это пустая
  структура-метка: `ConfigId<TowerTag>` и `ConfigId<EnemyTag>` разные типы, перепутать
  их нельзя (ошибка компиляции). Создать можно только через `tryParse`. Есть
  `operator<` (для `std::map`) и специализация `std::hash`. Здесь же `MechanicId`:
  его используют и определения (B), и механики (E). Остальные id объявляет слой B.

### Время и числа

- `Scalar` и `NumericUtils` (`Numeric.h`): `using Scalar = double` это единственное место
  выбора числового типа. `ceilTolerant` / `floorTolerant` игнорируют шум арифметики:
  `0.14 / 0.02` в double равно `7.000000000000001`, обычный `ceil` дал бы 8, а
  `ceilTolerant` даёт 7. Если число в пределах `relEps` от целого, берётся это целое.
- `Tick`: целое число тиков, не меньше нуля. Отдельный тип не даёт смешать тики с
  секундами. `Tick(2) - Tick(3)` бросает исключение, потому что результат был бы отрицательным.
- `FixedTimeStep`: шаг `dt` и единственное место перевода секунд в тики.
  `delayToTicks` допускает 0 (задержка), `intervalToTicks` даёт минимум 1 тик (интервал).

### Геометрия и гекс-сетка

- `Vec2`: точка или вектор. Есть `moveTowards(target, step)`, который не перелетает цель.
  Сравнение `==` точное: «примерно равно» в симуляции не используется.
- `Circle`: центр и радиус (радиус больше нуля, иначе исключение). `contains` и `overlaps`
  сравнивают квадраты расстояний, без `sqrt`. Нужен определению врага (`collisionShape`).
- `HexDirection`: шесть направлений в фиксированном порядке. Поиск пути всегда обходит
  соседей в этом порядке, поэтому при равных маршрутах выбор одинаков на любой машине.
- `HexCoord`: осевые координаты `(q, r)`, целочисленная арифметика, `neighbor`,
  `neighbors`, `distanceTo` по формуле `(|dq| + |dr| + |dq+dr|) / 2`. Есть `operator<`
  и `std::hash`.

### Версии

- `Version`: `major.minor.patch`, строгий разбор (без пробелов, знаков и ведущих нулей).
  Нужен для версии схемы файла и версий определений.

### Ошибки и коллекции

- `Diagnostic`: одно сообщение (серьёзность, код, путь к полю, текст).
- `DiagnosticList`: набор сообщений; валидатор показывает все ошибки за один проход.
- `Result<T>` и `Result<void>`: значение или `Diagnostic`.
- `Registry<TId, TValue>`: словарь с уникальными ключами на `std::map`, обход всегда
  в порядке ключей. Используется в блоке B для реестров определений.

## Что проверяют тесты

| Файл | Что проверяется |
|---|---|
| `test_numeric` | округление с допуском на реальных «плохих» числах, границы диапазонов |
| `test_ids` | допустимые и недопустимые id, разные типы у разных `Tag`, хеширование |
| `test_time` | `Tick`, перевод секунд в тики (минимум 1 для интервала) |
| `test_geometry` | `Vec2`, `Circle` |
| `test_hex` | порядок соседей, расстояния, сортировка и хеш `HexCoord` |
| `test_version` | разбор и сравнение версий |
| `test_diagnostics` | `Diagnostic`, `DiagnosticList`, `Result`, `Registry` (дубликаты, порядок обхода) |

## Расхождение с документом блока

В `A_foundation_detailed.md` пример округления записан как `0.75 / 0.05 = 15.000000000000002`.
В double это ровно `15.0`. Реальные примеры: `0.14 / 0.02 = 7.000000000000001`
и `0.1 * 3 / 0.1 = 3.0000000000000004`. Код и тесты используют их; смысл решения
(округлять с допуском) не изменился. Пример в документе блока стоит поправить.
